# swiss-stats: GPU statistics on 905M Swiss public-transport arrivals

Punctuality of every train, tram, bus, boat and metro arrival in Switzerland, measured
from the national real-time feed (opentransportdata.swiss, *Ist-Daten v2*), over 453 days
and **904,977,745 arrivals**, computed on a single Tesla P100 that shares its memory with
a production LLM service.

| | |
|---|---|
| **14,138×** | bootstrap confidence intervals for p95 delay on 445k groups: 0.7 s on the GPU vs 2.9 h naive on the CPU |
| **0 mismatches** | every GPU result cross-checked against an independent CPU computation (444,944 groups, n / p50 / p95) |
| **6 data-quality rules** | each found in the data, not assumed; one of them removed 8,821 records with delays of up to −56 years |

Engineering and statistical discipline carry equal weight in this project. A fast number
that is wrong is worse than a slow one, and a correct number nobody can audit is not much
better.

## What the data says

Network-level punctuality is stable year over year. Change is local.

| Level | Finding | Evidence |
|---|---|---|
| Modes | Trains arrive within 3 min 93.9% of the time, trams 91.2%, buses 86.1%. Zahnradbahn arrive *early* 23% of the time: on-time looks excellent, timetable accuracy does not. | whole period, 905M arrivals |
| Rail hubs | Zürich HB p95 = 206 s [205, 207]. Basel SBB is the outlier at 450 s [441, 458]: the heavy tail is international traffic (SBB EC trains: p95 = 32 min). | per-arrival bootstrap, B = 1000 |
| Hours | Weekday 1:00 is the worst hour (p95 6.0–6.5 min ± 0.2). The evening peak 17–18 h is 4.2–4.3 min and identical Mon–Fri once a year of data is in. | 62M train arrivals, 168 cells |
| Year over year | Aug–Sep 2026 vs 2025: 24 of 25 hubs, all 24 train hours and all modes unchanged after FDR. St. Gallen improved by 39 s [19, 55]. 21 lines materially worse (Lucerne's VBL 2/6/7/12: +64 to +180 s), 23 better (Lugano's TPL 2/4/5: −98 to −362 s; Neuchâtel's TRN 101/107: +18 to +20 pp on time). | day-block bootstrap, like-for-like panel, BH-FDR 5% |

Interactive report: `out/report.html` (generated by `src/f5_report.py` from the aggregates;
reruns after every refresh).

## Engineering

### Pipeline

```
opentransportdata.swiss ──► ingest.py ──► raw Parquet (one file per day, canonical schema)
  daily CSV (50-day window)      │
  monthly ZIP archive (backfill) │
                                 ▼
                         build_curated.py ──► curated/ (integer facts + append-only dimensions)
                                 │              905M rows, 1.6 GB, loads in 0.2 s
                                 ▼
          ┌──────────────────────┼──────────────────────┐
     f2_curated.py         f3_bootstrap.py          f4_yoy.py / f41_yoy_panel.py
     group statistics      quantile bootstrap       day-block bootstrap, panel, FDR
     (CuPy engines)        (custom CUDA kernel)     (cuBLAS SGEMM)
          └──────────────────────┼──────────────────────┘
                                 ▼
                         agg/*.parquet ──► f5_report.py ──► out/report.html
```

* **Ingest.** Polars parses a 630 MB daily CSV into a 28 MB zstd Parquet in ~1 s (23×
  compression). Every day is validated (timestamp parse failure < 0.1 %, absurd-delay
  count, share of Swiss stops) and logged to a manifest. A systemd timer with `MemoryMax`
  collects each new day; the archive backfill streams monthly ZIPs day by day without
  ever holding a month of CSV on disk.
* **Curated layer.** Strings are encoded once into append-only dimension tables
  (`dim_product`, `dim_line`, `dim_station`); the fact table holds only integers. New days
  never re-code history. Rebuilding 453 days takes 2.5 min in batches of 20 days, with a
  4.8 GB RAM peak instead of the ~170 GB a single pass would need.
* **Shared GPU.** The P100 also runs an Ollama inference service whose VRAM use swings
  between 0 and 16 GB during the day. Every GPU script reads the free memory at start,
  takes `min(configured budget, free − 1 GB)`, waits up to 30 min if less than 1 GB is
  available, and partitions the work by station so that the result is exact at any budget.
  Out-of-memory doubles the partition count and retries. The guard refuses to start on any
  GPU other than the one pinned by UUID.

### Three GPU engines

| Engine | Problem | Idea | Result |
|---|---|---|---|
| **Sort engine** | per-group n, mean, on-time share, p50/p90/p95 for 445k station × mode × hour groups | pack `(group id << 14) \| (delay + 1800)` into one int64, one radix sort gives groups contiguous and delays ordered; quantiles become O(1) index reads, sums are int64 prefix sums | 6 groupings with all metrics in 39 s on 905M rows; 2.1× faster than Polars on 12 cores per grouping, memory-bound as expected |
| **Histogram engine** | the same statistics for global groups (mode × weekday × hour, 2,488 lines) | delays are integers in a 9,001-bin window, so a `bincount` histogram is exact and mergeable across partitions; quantiles come from the cumulative histogram | exact at any partition size with ~600 MB of VRAM |
| **Bootstrap kernel** | 95 % CI for the p95 of every group, B = 1000 | the k-th order statistic of n uniform indices is `floor(n·U)`, `U ~ Beta(k+1, n−k)`: one Beta draw and one lookup per replicate instead of a resample and a partition. Custom CUDA kernel (splitmix64 RNG, Marsaglia–Tsang gamma, FP32), one thread per replicate | **470M replicates in 0.74 s**; 238× from the algorithm, 59× from the GPU on top, 14,138× in total; 97.7 % agreement with a naive bootstrap on 300 validation groups |

The day-block bootstrap for the year-over-year comparison is a fourth pattern: per-day
histograms `H[slot, day, bin]` and multinomial day weights `W[replicate, day]` turn all
1,000 replicates into one `W @ H` matrix product (cuBLAS SGEMM), 9.3× faster than
multithreaded CPU BLAS.

### What the hardware taught

* Everything is FP32 with integer accumulators, so the same kernels run unchanged on an
  Ampere card whose FP64 is 1/64 of FP32. The build targets `sm_60` and `sm_86` in one
  fat binary; switching GPUs is a UUID in `config.yaml`.
* Once the kernels ran in under a second, 90 % of wall time was host-side data movement
  (boolean masks over 905M rows per partition). One stable radix argsort by partition id
  made every partition a contiguous slice and cut F3 from 43 s to 8 s. The next step is to
  store the curated layer clustered by station so no sort is needed at all.
* The CPU reference computation is not a benchmark prop: it runs on every invocation and
  the script reports the mismatch count. It has been 0 on every run since the first.

## Statistical discipline

### Six data-quality rules, each found in the data

| # | Rule | How it surfaced |
|---|---|---|
| 1 | A Swiss stop has UIC prefix **85 as a string**, not by integer division | BPUIC comes as 7 digits (station) or 9 (platform); integer division gave 19 % "Swiss" stops instead of 98 % |
| 2 | \|delay\| > 1 day is a **broken timestamp**, not a delay | 8,821 arrival records, the worst at −56 years, almost all on weekends with bus replacement; they moved the mean by 0.1 s and no p95 at all |
| 3 | One **canonical raw schema** across format evolution | the v2 feed gained a `SLOID` column on 2025-10-13; 92 earlier day files had to be normalised before any reader would open the set |
| 4 | **Product labels** are normalised | `Bua` appeared as an eighth mode on 5,250 rows |
| 5 | Prefix 85 means *in the Swiss register*, not *in Switzerland* | Italian stations on the Luino line carry 85xxxxx codes and surfaced among the worst stops |
| 6 | **Line identity by route fingerprint**, not by vendor name | 12 renames found by stop-set Jaccard ≥ 0.8 (RE41→R41, 38→28, PAG→PAG/BCS); they explain ~1 % of the apparent volume drift, the other 99 % was new real-time coverage |

### Four lessons

1. **Quantiles, not means.** The 8,000 garbage values from rule 2 shifted the mean and not
   a single p95. Punctuality is reported as p95 and on-time shares throughout.
2. **Design effect.** Arrivals within one day are correlated (weather, incidents,
   knock-on delays). A per-arrival bootstrap gave intervals 2.5–10× narrower than a
   day-block bootstrap on the same slots. On 120M arrivals the naive method would have
   called almost any difference significant; the honest unit of replication is ~60 days.
3. **Like-for-like plus FDR.** Raw bus arrivals grew 17 % between the two summers; on a
   panel of lines with stable route (Jaccard ≥ 0.8) and volume (±25 %) they grew 1.3 %.
   After the panel and Benjamini–Hochberg at 5 %, **35 of 79 naive claims of change
   disappeared**, 16 of them because the route had been rebuilt under the same line number
   (most of Geneva's network).
4. **A reporting policy that is itself data-driven.** A p95 is shown only with n ≥ 200
   (≥ 10 observations above it); it is called *precise* only when the measured CI
   half-width is ≤ max(60 s, 20 % of p95) and the CI does not touch the clip ceiling. With
   50 days this kept 74 % of arrivals; with 453 days, 99.4 %, and CIs narrowed by exactly
   √9.6 ≈ 3.1×, as theory says.

## Repository layout

```
src/
  ingest.py            daily CSV → raw Parquet, validation, manifest
  backfill.py          monthly archive ZIPs → raw Parquet, overlap check vs daily
  normalize_raw.py     one canonical schema over all day files
  build_curated.py     raw → curated integer layer, append-only dimensions, --rebuild
  line_identity.py     DQ rule 6: renames by route fingerprint
  f2_aggregates.py     GPU engines: sort, histogram, adaptive VRAM budget, partitions
  f2_curated.py        F2 on the curated layer, CPU cross-check, report tables
  f3_bootstrap.py      CUDA bootstrap kernel, three-level benchmark, validation
  f31_ci_rule.py       reporting policy (n floor, precision tier), CI-vs-n plots
  f4_yoy.py            day-block bootstrap (SGEMM), design effect
  f41_yoy_panel.py     like-for-like panel, z-tests, BH-FDR, claim survival
  f5_report.py         self-contained HTML report from agg/
config/config.yaml     GPU UUID, VRAM budget, data root, reporting policy
systemd/               swiss-stats-daily.service / .timer
```

## Reproduce

```bash
# Python 3.9+, CUDA 12.x driver, a Pascal-or-newer GPU
pip install cupy-cuda12x polars pyarrow duckdb matplotlib pyyaml requests
cp config/config.example.yaml config/config.yaml      # set gpu_uuid, data_root
python src/ingest.py all          # last ~50 days from the daily feed
python src/backfill.py            # 2025-07 … today from the monthly archive (~1 h)
python src/normalize_raw.py
python src/build_curated.py --rebuild
python src/f2_curated.py && python src/f3_bootstrap.py && python src/f31_ci_rule.py
python src/f4_yoy.py && python src/f41_yoy_panel.py
python src/f5_report.py           # → out/report.html
```

Expected resources for 15 months: ~220 GB of transient downloads, 13 GB raw Parquet,
1.6 GB curated, ~50 GB RAM peak in F2 (the CPU reference), 4–6 GB VRAM.

## Data

*Ist-Daten v2*, Open Data Platform Mobility Switzerland (opentransportdata.swiss),
licence: open use with attribution. An arrival enters the statistics only if its stop is
in Switzerland, its status is `REAL` (measured, not forecast), the trip was not cancelled
and the vehicle actually stopped.
